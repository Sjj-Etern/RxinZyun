## 一、使用前提

### 1. 网络环境

| 路由器 AP 隔离 | 必须关闭（否则客户端间无法通信） | 已关闭 |

### 2. 后端运行前提
- **端口 8080 必须空闲**：若 8080 被占用，后端启动时 `uvicorn bind` 失败会触发 `lifespan shutdown`，导致电梯 TCP 服务（10833）被一起停掉，ESP32 将连接被拒（`errno=104`）。
- 启动后需确认 10833 / 10832 / 8080 三个端口均监听 `0.0.0.0`。
- 检查命令：
  ```powershell
  Get-NetTCPConnection -LocalPort 8080 -State Listen      # 有输出=被占，需先杀掉
  Get-NetTCPConnection -LocalPort 10833 -State Listen     # 启动后端后必须有输出
  ```

### 3. ESP32 固件前提
- 已烧录含**固定后端 IP 直连**的固件（[wifi_.h](file:///d:/rxzy_test/elevator_access_control/components/BSP/WIFI/wifi_.h) 中 `ELEVATOR_SERVER_IP = "192.168.1.106"`，[main.c](file:///d:/rxzy_test/elevator_access_control/main/main.c) 启动时调用 `tcp_client_set_server` 直连 TCP，跳过 UDP 发现）。
- 若后端 PC IP 变化，需同步修改 `wifi_.h` 的 `ELEVATOR_SERVER_IP` 并重新烧录。

## 五、问题所在

### 问题1（核心）：go_floor 跨楼层移动时 TCP 连接断开

**现象**：发送 `go_floor` 到不同楼层（楼层差>0）时，命令 ACK 正常返回，但 ESP 执行 toFloor 红外移动期间，TCP 连接被重置，紧随其后的命令超时。ESP 约 5 秒后自动重连（新端口），重连后恢复正常。

**后端日志证据**：
```
[11:04:40.862] DONE #5: cmd=go_floor, duration=80ms        ← ACK 已回
ESP32 连接异常: [WinError 64] 指定的网络名不再可用。        ← toFloor 执行期间 TCP 被重置
[11:04:47.370] ESP32 已断开: 192.168.1.110:49380
[11:04:50.607] ESP32 已连接: 192.168.1.110:49381           ← 5秒自动重连（新端口）
[11:04:53.112] TIMEOUT #6: cmd=status, 10012ms 无 ACK      ← 断连期间的命令超时
```

**根因分析**：
- ESP32 收到 `go_floor` 后先回 ACK（符合"先 ACK 再执行"约定），再执行 [emission.c](file:///d:/rxzy_test/elevator_access_control/components/BSP/EMISSION/emission.c) 的 `toFloor`（红外 NEC 发射模拟按键）。
- `toFloor` 在 [tcp_client.c](file:///d:/rxzy_test/elevator_access_control/components/BSP/WIFI/tcp_client.c) 的 recv 循环内**同步阻塞执行**，期间 TCP 任务无法及时处理 lwip 协议栈，导致连接被判定异常重置（WinError 64）。
- 同楼层（楼层差=0）时 `toFloor` 不发射红外，不阻塞，故不断连。

**影响**：
- 单独发 `go_floor` 可成功（ACK 在断连前返回）。
- `go_floor` 后立即发的命令会超时（需等 ESP 重连，约 5 秒）。
- 实际电梯联动（ROS 触发 lift-arrive → go_floor）中，go_floor 后若有后续命令会受影响。

**修复方案**（✅ 已实施并验证）：
采用「独立 FreeRTOS 任务异步执行 toFloor」方案，彻底分离 TCP 通信与耗时硬件操作：

| 修改文件 | 修改内容 |
|----------|----------|
| [emission.h](file:///d:/rxzy_test/elevator_access_control/components/BSP/EMISSION/emission.h#L70-L72) | 新增 `floor_move_task_start` / `request_go_floor` 函数声明 |
| [emission.c](file:///d:/rxzy_test/elevator_access_control/components/BSP/EMISSION/emission.c#L76-L115) | 新增 `floor_move_task` 独立任务：阻塞等待通知 → 执行 `toFloor`；`request_go_floor` 设置目标楼层并通过 `xTaskNotifyGive` 唤醒任务 |
| [tcp_client.c](file:///d:/rxzy_test/elevator_access_control/components/BSP/WIFI/tcp_client.c#L229-L250) | `go_floor` 命令处理改为：先回 ACK（避免后端超时）→ 调 `request_go_floor` 异步提交（非阻塞）→ recv 循环立即继续 |
| [main.c](file:///d:/rxzy_test/elevator_access_control/main/main.c#L201) | `app_init` 末尾调用 `floor_move_task_start()` 启动楼层移动独立任务 |

**修复后验证**（2026-08-14，重新编译烧录后实测）：

| 命令 | seq | ACK 耗时 | 移动后连接 | 楼层 | 结果 |
|------|-----|----------|------------|------|------|
| go_floor 3（1→3，上行2层，约9.7s） | #17 | 189ms | ✅ 存活 | 3 | ✅ |
| status（移动后查询） | #18 | 190ms | ✅ 存活 | 3 | ✅ |
| go_floor 1（3→1，下行2层，约9.1s） | #19 | 104ms | ✅ 存活 | 1 | ✅ |
| status（移动后查询） | #20 | 68ms | ✅ 存活 | 1 | ✅ |

后端日志全程无 `WinError 64`、无断开、无 TIMEOUT，同一连接 `192.168.1.110:62170` 贯穿全部命令。对比修复前（#5、#14 后必断连 + 后续命令 TIMEOUT），跨楼层断连问题彻底解决。

### 问题2（次要）：后端 8080 占用导致电梯服务连锁停摆

**现象**：8080 被残留 python 进程占用时，后端 `uvicorn bind 8080` 失败触发 `lifespan shutdown`，电梯 TCP 服务（10833）被一并停止，ESP32 连接报 `errno=104`（ECONNRESET）。

**修复方向**：启动后端前务必确认 8080 空闲；或后端代码层面让电梯 TCP 服务独立于 HTTP 服务（8080 失败不拖垮 10833）。

### 5. 修复的两个死锁问题

#### 死锁1：主循环阻塞

**现象**：后端收到 lift-arrive 后，Step 7 `await event.wait()` 阻塞主消息循环，导致 nurse_arrive 消息无法被接收，流程永久卡死。

**根因**：[ros_listener.py:724](file:///d:/rxzy_test/hospital_dashboard_backend/app/services/ros_listener.py#L723-L727) `await self.handle_ros_message(data)` 同步执行，lift-arrive 处理耗时较长（含多个 await sleep），阻塞了主循环的 `ws.recv()`。

**修复**：
```python
# 修改前
await self.handle_ros_message(data)

# 修改后（异步处理，不阻塞主循环）
task = asyncio.create_task(self.handle_ros_message(data))
task.add_done_callback(self._on_msg_task_done)
```
新增 `_on_msg_task_done` 回调方法捕获任务异常，避免静默失败。

#### 死锁2：event 竞态条件

**现象**：死锁1修复后，nurse_arrive 能被接收但 nurse-success 仍超时。

**根因**：ESP32 当前楼层已是 3 楼（目标楼层），后端跳过 Step 6 楼层移动直接进入 Step 7。nurse_arrive 在 Step 6 期间到达并执行 `event.set()`，但 Step 7 的 `event.clear()` 清除了已 set 的 event，导致 `wait()` 永久阻塞。

**时间线证据**：
```
11:52:23.410  nurse_arrive 到达 → event.set()
11:52:23.556  status 查询返回 floor=3 → 跳过去楼层
11:52:23.5xx  Step 7: event.clear() ← 清除了已 set 的 event！
11:52:23.5xx  Step 7: await event.wait() ← 永久等待
```

**修复**：将 `event.clear()` 从 Step 7 移到 lift-arrive 流程开头（Step 1 之前），保证流程中 nurse_arrive 的 `set()` 不被覆盖：
```python
# 修改前（Step 7 内）
self._nurse_arrive_event.clear()
await self._nurse_arrive_event.wait()

# 修改后（流程开头清除，Step 7 只 wait）
elevator = get_elevator_controller()
self._nurse_arrive_event.clear()  # 移到这里
# ... Step 1~6 ...
await self._nurse_arrive_event.wait()  # Step 7 只等待
```

## 七、结论

1. **HTTP 控制链路已打通**：测试脚本 → 后端 API → TCP → ESP32 全链路正常，`state`/`status`/`open_door`/`close_door`/`go_floor`/`all` 全流程均通过。
2. **DHT11 温湿度功能正常**：status 查询返回 29°C / 64%，数据准确。
3. **ESP32 固定 IP 直连方案有效**：彻底解决了 UDP 发现收不到响应导致的连接失败问题。
4. **✅ go_floor 跨楼层断连问题已修复**：将 `toFloor` 红外移动改为独立 FreeRTOS 任务异步执行，TCP recv 循环不再被阻塞。实测跨楼层（1→3、3→1）移动后连接全程存活，ACK 在 47~190ms 内返回，无 `WinError 64`、无超时。

6. **运维注意**：每次启动后端前确认 8080 空闲，避免电梯服务被连锁停摆。
7. **ESP-IDF 编译注意**：本机 IDF 安装的 Python venv 为 `idf5.5_py3.11_env`，而系统 PATH 默认 Python 为 3.10，直接 `export.ps1` 会报 venv not found。编译/烧录前需设置 `$env:IDF_PYTHON_ENV_PATH = "D:\SoftWare\Espressif\python_env\idf5.5_py3.11_env"` 再 source export.ps1。
